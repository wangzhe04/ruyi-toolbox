# D0 第三轮 · 2026-09-25：让合成集真正测得出质量

状态：**两候选在新语料 40 页 dev 上全部跑通；对齐仍为机器提议、未人工复核；holdout 未动；仍未选型。** 汇总证据（仅元数据）见 [v2-dev-results.json](v2-dev-results.json)。第二轮的 v1 分数已作废：v1 每页同一模板，两引擎都接近满分，区分不了质量。

## 为什么重做语料

第二轮的临时分数几乎全是 1.00，唯一的差别来自样本缺陷（双栏逐行对齐，横读也说得通）。合成集如果测不出差别，就没有资格给选型提供任何方向。生成器 v2（`generate_corpus.py`，v1 保留为 `generate_corpus_v1.py`）改为：

- 每页独立种子排版，5 种本机字体，逐字节可复现（已实测两次生成哈希一致）；
- 标注粒度改为“一行 / 一格”，引擎合段落不吃亏，读串栏在顺序上暴露；
- 多栏：2–3 栏、多行段落、长短行距不齐，只有先读完一栏才对；
- 合并表格：两级表头、跨行分组、跨列合计、空白格，四分之一无竖线；混排页表格无竖线；
- 行内数字单独标注（`numbers`），编号 / 日期 / 版本号作整词，连字符不当负号；
- 扫描加噪声、模糊、JPEG；倾斜 ±1–4°，并按旋转精确换算 `observedBbox`，倾斜页位置也能核对。

`render_qa.py` 叠加画出 gold 框与阅读顺序，本轮逐类目检了 pilot 页：框贴字、顺序先栏后栏、空白格有标注、倾斜框跟随文字；修正了“，”出现在行首的排版缺陷。

## 评测工具本身的修正（都影响分数，已加回归测试）

逐条追查“低分是不是引擎的错”时发现并修了 5 处工具问题：

1. 一格一字的短标注（如“%”“Q1”）会抢先占用正文长句里的子串，导致整行被判缺失——Docling 混排页 CER 从 9.1% 虚高，修后 1.1%。现在单元格 gold 只配引擎单元格或整块独立文本，短 gold 最后分配。
2. 同一短语在一个段落里出现两次时，只算一个候选，被占后不再找下一处 → 改为遮住已占片段重算。
3. 同一句话在页面上出现两次时，按 gold ID 字典序抢位 → 代价相同时优先位置吻合的引擎块。
4. “块框不得远大于 gold 框”这一条原本拿单行比整段，段落末尾短行必然不合格；又误伤引擎的整格框（gold 只框格内文字）→ 改为比较引擎框与配给它的全部 gold 行外包框，单元格不做此检查。
5. `run_candidate.py` 在运行结束时才计算适配器哈希，运行期间改代码会被记到这次运行名下 → 改为启动时计算。`v2-dev-paddle/run.json` 里的 `adapterSha256` 因此记成了后来的版本，实际使用的是 `2865bf77…`（默认配置参数不变），已在结果文件注明。

新增诊断指标 `cellTextAccuracy`（格内文字对，不管结构）和 `cellNeighbourAccuracy`（相邻格仍相邻，容忍整体错位），把“认错字”和“表格结构错”分开。自动测试 54 → 62 项，全部通过。
