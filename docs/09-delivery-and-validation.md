# 09 · 公共交付、跨仓接入与验证

> 状态：未来实现的约束与交办单，不改写现行 [登记约定](00-component-registry.md)。先随第一个新组件落实必要部分；出现第二个消费者后再抽公共库。

## 1. G0：先补契约，不先造平台

| 工作 | 仓库归属 | 必须明确的结果 |
| --- | --- | --- |
| 安装目录与任务输出边界 | 两仓公开约定 | 现行“目录外唯一写入登记文件”限制应限定安装/后台写入；用户授权的任务输出另有明示规则。修订前新组件只写自身结果目录 |
| 输入授权 | toolbox 自身校验；主仓可补授权桥 | 固定 allowed input roots、规范化路径、拒绝越界/junction 跳转；不能以 MCP 调用参数自行扩大授权 |
| 输出授权与覆盖 | toolbox + 主仓 | 固定 output roots、新文件默认、冲突拒绝；自动回撤必须经过主仓实际映射和测试 |
| ASR 能力发现 | 主仓公开接口 + toolbox 适配 | 动态端口、能力、启停状态；不读取主仓私有配置、不给组件无关密钥 |
| TTS 消费 | 主仓 | 提供专用能力、代理、播放器与取消契约后才能登记为可用 |
| 专业工具使用说明 | 主仓资源/组件 README | 何时使用、输入限制、何时降级，工具描述保持简短 |

外部 MCP 的 `readOnlyHint` 等声明只是提示，不是权限豁免。当前如意 Claude 路径的外部 MCP 有 exec 层边界，须分别验证 Provider 与 Agent CLI 的真实行为；不要为让新组件“随时可用”而放宽既有全局权限。

## 2. 新组件最小布局

拟议布局：`pyproject.toml`（显式列 packages）、`ruyi_<name>/__main__.py`、`scripts/install.ps1`、可选 `scripts/download-model.ps1`、`tests/`、`README.md`。安装动作提供 `register/unregister/doctor`，模型在 `models/`，缓存和作业在组件自己的运行数据目录。

遵守现有包发现规则，不把虚拟环境移机；模型登记参数需要精确配置打包器的组件表。新增 Python 版本时同步修正 wheel 目标和离线校验，不能假定所有组件永远适用 3.12。PS1 继续 UTF-8 BOM + CRLF。

拟新增 `doctor --json` 返回版本、依赖、模型、可用设备、磁盘需求、路径权限、离线准备状态、错误码；不得输出用户正文/令牌。register 只在必需项通过后原子写入登记文件，失败不留“看似安装成功”的记录。

## 3. 长任务共同语义

状态：queued → running → succeeded/partial/failed/cancelled；取消中使用 cancelling，进程停止后才写 cancelled。MCP submit 快速返回 jobId，status/read 分页取结果；重启发现 running 但 worker 不在时标 interrupted，校验检查点后可恢复。

jobId 与幂等键分开；幂等键包含输入哈希、选项、引擎/模型版本。工作进程只写 staging，完成后原子发布产物 manifest；主控日志仅记录元数据。定义每作业和每组件的磁盘预算、超时、并发上限与缓存 TTL；磁盘不足先拒绝新作业，不能自动删除用户原文件。

单组件先采用一个重任务 worker。跨组件显存治理分两步：第一版显式 CPU/单 GPU 作业档和可诊断 OOM、空闲卸载；有两个以上 GPU 消费者后才实现主仓资源租约或公开资源协调协议。现有主仓资源租约不能未经审阅就当成 GPU 分配器；也不能声称多个组件天然互斥。

## 4. 输出与权限验证

授权来源应是安装配置或主仓明确授权，不能相信模型传入的 `allow=true`。路径应以最终解析的绝对路径校验，并检查 Windows 盘符、UNC、符号链接/junction、大小写与父目录边界；首版拒绝不能安全验证的重解析路径。

结果读取不通过任意路径接口，而通过 job/document/dataset ID 映射组件已有产物。导出使用临时文件+原子更名，不覆盖现有文件。输入文件只读，模型缓存与用户材料分开清理。若必须覆盖，主仓检查点和失败恢复是独立交付项，验证前不提供该动作。

“本地处理”仅保证组件不主动上传；MCP 返回的片段可能进入用户选择的云模型。组件 README 和如意说明应准确表达这一边界，不能宣传完整对话绝不出机。

## 5. 离线打包的增量方案

| 次序 | 工作 | 验收 |
| --- | --- | --- |
| B0 | 复核当前打包器工作区改动，再基于已合入版本扩展 | 不覆盖并行工作的脚本；记录实际基线 |
| B1 | 每组件锁包/模型、平台与 Python ABI，输出 SHA-256 manifest 和第三方声明 | 同一锁定输入可复建；不把“本机可跑”当跨机证明 |
| B2 | wheel、模型和辅助二进制预取；禁止运行期自动下载 | 全新缓存、禁网络下完成安装和真实任务 |
| B3 | 可选携带 Python 运行环境 | 在无 Python/uv 的干净 Windows 用户环境验证，不仅在开发机 dry-run |
| B4 | 升级/回退与清理 | 新目录验证成功后登记切换；旧版本保留至新任务通过；卸载不碰原始材料 |

Python 携带方案对比：保持“目标机预装 Python”最简单，但不能叫完全自包含；携带常规运行时再建 venv 需验证实际分发/安装方式；嵌入式运行时需按官方部署方式预装依赖，不能假定它支持常规 pip/venv 工作流。B3 先做独立探针决定路线，可参考主仓 ACC 的打包经验但不直接照搬未核实路径。[官方说明](https://docs.python.org/3.12/using/windows.html#the-embeddable-package)

安装目录升级与索引 schema 升级分开。新组件版本不原地迁移唯一旧索引：先备份或建立新代次，验证后切换；恢复旧版本必须同时恢复相容 schema。含个人资料的索引、任务缓存默认不随“组件迁移包”打包，用户材料迁移应另行显式选择。

## 6. 验证矩阵

| 层级 | 内容 | 执行时机 |
| --- | --- | --- |
| 单元/契约 | 假后端验证 schema、状态、分页、来源、错误、取消、幂等 | 每次改动；不需要真模型 |
| 本机真实能力 | 各专题开发集/盲测集、冷/热性能、资源、失败样本 | 首发、模型或内核升级 |
| 如意集成 | Provider 和 Agent CLI 的发现、工具调用、权限、产物读回 | 首发、工具/登记契约变化 |
| 部署矩阵 | Windows 11 x64 CPU（16GB）、NVIDIA 独立档；中文/空格/较长路径 | 对应档位发行前；硬件型号写进报告 |
| 离线迁移 | 无共享缓存、无网络、全新用户；安装、重启、任务、卸载 | 每个发行包 |
| 降级 | 缺模型、停用组件、模型切换、内存/磁盘不足、父进程退出 | 首发和生命周期改动 |

Windows 10、AMD、ARM64 未验证就标未验证；不沿用 ASR 的某个硬件结论替其他引擎背书。不能提供干净机器验证时发行标 preview，并列出缺项。

## 7. 评测记录模板与完成定义

每次决策报告至少包含：日期、组件/上游 revision、依赖锁和模型哈希、硬件/OS/驱动、CPU 线程、缓存状态、样本 manifest、运行配置、逐样本结果、失败记录、质量指标计算脚本版本、p50/p95、资源峰值、选型结论与限制。

每个专题开始前指定实施者和验收复核者；人力不足可由同一人分轮复核，但盲测集不可用于调参。质量不足优先缩小支持范围，不悄悄降低门槛；调整门槛必须附原因和前后结果。

发布完成必须同时满足：功能可用、真实样本过关、双引擎接入过关、离线包过关、停用/卸载/回退过关、来源和许可齐全。只写完代码或只通过假模型测试不能标“可用”。
