# 03 · Toolbox 能力拓展路线图

> 2026-09-21。状态：规划，未实施。本文确定产品顺序和工程边界；引擎首选基于官方资料调研，最终发布版本必须通过各专题的本机评测门槛。本次没有下载候选模型、运行候选引擎或测出性能数据。

文档定稿：2026-09-22；调研与源码盘点开始于 2026-09-21。

## 1. 定位与目标

Toolbox 为如意提供可选的、本地运行的专业处理能力：把复杂材料变成能计算、能检索、能核对的结果。主仓继续负责交互、权限、编排、任务调度与交付展示。依赖重、需要模型、不是人人需要的运行时放在 toolbox。

优先覆盖中文 Windows 办公用户。默认以 CPU 可用为底线，GPU 是提速或增强选项；“离线”指组件处理链离线，不意味着用户选用云端对话模型时文本不会外发。

## 4. 已确定的架构决策

1. D1/K1/A1/T1 采用标准 stdio MCP，目录建议为 `mcp/document-parser`、`mcp/knowledge-library`、`mcp/audio-processing`、`mcp/data-analysis`。目录名是计划，不表示已存在。
2. 首选引擎分别为 Docling、SQLite + 小型 embedding、现有 ASR、DuckDB；选型理由和替换条件见 [调研对比](04-research-and-decisions.md)。不把框架直接注册的全部工具无筛选地接入如意。
3. 资料库先消费解析组件输出的稳定材料格式，不直接读取另一个组件的私有数据库，不让主仓依赖任何 Python 包。
4. MCP 面向模型提供完整任务动作；仅提供 embedding HTTP 接口不能算资料库完成。TTS 面向如意自身，因此走 `service + provides`，主仓支持之前不宣称自动可用。
5. 安装、缓存、索引默认在组件目录内。用户输入目录只读；用户指定的产物目录需要独立写入授权。现有 [00 号约定](00-component-registry.md) 对目录外写入有严格表述，G0 必须先澄清“安装登记”与“用户授权任务输出”的边界，不能由实现自行绕过。
6. 第一版外部 MCP 不宣称自动继承主仓文件检查点。默认禁止覆盖已有产物；如需覆盖回撤，先补主仓映射和双引擎验证。

## 5. 决策和验收流程

每个专题都按以下次序执行，不能以“上游支持”代替目标机器验收：

1. 固定用户场景、输入输出、排除项，建立可公开或已授权样本。
2. 核对候选版本、模型 revision、许可证、Windows wheel、离线依赖；记录来源与日期。
3. 用同一数据、硬件、线程数对比首选和至少一个实际可行备选；保留冷/热启动和失败结果。
4. 根据专题门槛写决策记录：选择、证据、放弃原因、剩余限制；没有通过就缩小交付范围或改选，不虚报完成。
5. 实现最小组件与契约测试，接入如意两条执行路径，再做真实场景和迁移验证。
6. 锁版本、附结果和第三方声明，更新 README 状态后发布；升级时复跑同一套样本。

当前完成的是第 1 步的方案定义及第 2 步的官方资料预研；第 2 步的精确发布锁定和第 3 步以后仍是后续实施工作。各专题的数字是拟定验收目标，不是现有能力或实测结果。

下一次开发从 D0 开始：建立 60 页六类中文样本清单和标注规则，对 Docling / PP-StructureV3 做 Windows CPU 安装及 12 页预试验；同时核验 MinerU 的当前许可和独立适配成本。输出逐页结果、资源记录与选择理由，再冻结 D1 引擎版本。
